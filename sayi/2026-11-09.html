İDDİAAI DESTEKLİ GELİŞTİRME & GÜVENLİK

Claude Code’da “Yes, and don’t ask again” ile onaylanan komutlar sırlarıyla birlikte GitHub’a gitti: 1.122 açık dosyada gerçek parola ve anahtar

Apiiro’nun araştırmasına göre “don’t ask again” ile onaylanan Bash komutları, içlerine yazılmış parola ve token’larla birlikte .claude/settings.local.json dosyasına kaydediliyor ve bu dosyalar herkese açık repolara ulaşıyor. Dosyayı git dışında tutan koruma yalnızca geliştiricinin kendi makinesinde çalışıyor.

Güvenlik şirketi Apiiro’dan Shmulik Cohen ve Matan Giladi’nin 5 Kasım’da yayımladığı araştırmaya göre GitHub’daki 104.185 herkese açık .claude/settings.local.json kopyasının 1.122’sinde gerçek bir sır bulunuyor. Runtimewire’ın aktardığına göre Apiiro’nun daha geniş sayımı 1.994 herkese açık repoda 2.539 sırra ulaşıyor. Apiiro’nun raporuna doğrudan erişemedik; rakamlar raporu aktaran yayınlardan alındı ve bunları bağımsız olarak doğrulayan bir kaynak bulamadık.

Mekanizmanın kendisi Claude Code dokümantasyonunda yazıyor: bir Bash komutu için “Yes, and don’t ask again” seçildiğinde onay, .claude/settings.local.json dosyasına bir allow kuralı olarak kaydediliyor. Araştırmayı aktaran yayınlara göre kural komutu olduğu gibi sakladığı için komutun içine yazılmış bir parola ya da token da dosyaya giriyor.

Dokümantasyona göre Claude Code bu dosyayı bir git reposunda ilk yazdığında **/.claude/settings.local.json kalıbını geliştiricinin global git excludes dosyasına ekliyor; dosya elle oluşturulduysa .gitignore’a eklemek kullanıcıya kalıyor. Runtimewire açığı şöyle özetliyor: ignore kuralı tek bir geliştiricinin makinesinde, dosya ise projede yaşıyor.

Haberi değerlendirirken bir çekinceyi de not etmek gerek: Apiiro, Claude Code ve Cursor gibi AI kodlama araçlarına yönelik güvenlik ürünleri satan bir şirket. Nisan’da bu araçların okuyup çalıştırabildiği agent skill’leri içeren bir CLI duyurmuştu.

Kaynaklar: Apiiro araştırması · Runtimewire · Claude Code dokümantasyonu · settings · SiliconANGLE · Apiiro CLI

İDDİAYEREL ÇIKARIM

llama-modchip: 284 milyar parametreli DeepSeek-V4-Flash, GPU olmadan 64 GB RAM’de

Açık kaynak llama-modchip projesi, ggml/llama.cpp için kernel yamaları, quantization araçları ve çalışma zamanı yardımcılarından oluşuyor. Ana hedef, 284,33 milyar parametreli ve 13,17 milyar aktif parametreli MoE modeli DeepSeek-V4-Flash’ı yalnızca CPU ile çalıştırmak.

README’ye göre checkpoint, Unsloth’un 76,87 GiB’lik sürümünden 1,71 bpw ortalamayla 56,56 GiB’ye sıkıştırılıyor; routed expert’ler çoğunlukla IQ1_S, hassas katmanlar daha yüksek bit formatlarında tutuluyor. 256K context’te tepe bellek kullanımı yaklaşık 57,6 GiB olarak veriliyor. Hız artışı için AVX-512 kernel’leri, bir FlashAttention varyantı ve n-gram tabanlı bir speculative decoding taslakçısı kullanılıyor.

Proje, 16 çekirdekli bir Zen 5 makinede 9,06⁠–⁠9,95 tok/s decode, taslakçıyla 14,7 tok/s’ye kadar hız bildiriyor. DeepSeek rakamları geliştiricinin kendi ölçümleri; bağımsız doğrulama yok. Üretilen modeller yalnızca projenin yamalı binary’leriyle çalışıyor, standart llama.cpp, Ollama ve LM Studio bunları reddediyor. Lisans Apache-2.0.

Kaynak: GitHub · synchopate/llama-modchip

GITHUB ACTİONS

pull_request_target için ilk brownout bugün 16:00⁠–⁠18:00 UTC’de: public repolarda workflow’lar çalışmayacak

GitHub’ın duyurusuna göre 2 Aralık’tan itibaren public repolarda pull_request_target olayı, bir Actions event policy açıkça izin vermedikçe varsayılan olarak engellenecek. Geçişten önce iki brownout planlandı: bugün, 9 Kasım 16:00⁠–⁠18:00 UTC (İstanbul saatiyle 19:00⁠–⁠21:00) ve 16 Kasım aynı saatlerde. Bu pencerelerde engellenen çalıştırmalar bir hata notuyla başarısız oluyor ve workflow yürütülmüyor; pencereler dışında kural yeniden evaluate moduna dönüyor ve workflow’lar uyarıyla çalışıyor.

Değişiklik GitHub Free, Team ve Enterprise Cloud’daki public repoları etkiliyor; private ve internal repolar ile GitHub Enterprise Server kapsam dışında. Bu workflow’ları çalıştırmaya devam etmek isteyenlerin ilgili Actions event policy’ye açık bir izin eklemesi, belirli workflow’ları hedeflemek için de workflow dosyası hedeflemesini kullanması gerekiyor. Hangi çalıştırmaların engelleneceği Insights üzerinden görülebiliyor.

OPENJDK · JDK 28

JDK 28’in özellik listesi şekilleniyor: Rampdown Phase One 3 Aralık’ta, 10 JEP hedeflendi

OpenJDK’nın JDK 28 sayfasına göre ana hattan dallanma anlamına gelen Rampdown Phase One 3 Aralık’ta, genel erişim (GA) ise 9 Mart 2027’de. Sayfanın 2 Kasım tarihli son güncellemesine göre JDK 28’e hedeflenen JEP’ler şunlar: Value Objects (Preview, JEP 401), Shenandoah’ta generational modun varsayılan olması (535), JVM’de katı alan ilklendirme (Preview, 539), Simple JSON API (Incubator, 540), macOS/x64 portunun kaldırılmak üzere kullanımdan kaldırılması (541), kriptografik nesneler için PEM kodlaması (542), Structured Concurrency (543), Ahead-of-Time Code Compilation (544), ZGC ile daha hızlı açılış ve ısınma (545) ve ZGC için uyarlanabilir heap boyutlandırma (546).

Spring Boot servisleri için en doğrudan ilgili madde JEP 544: eğitim çalıştırmasında derlenmiş optimize native kod AOT cache’e yazılıyor ve sonraki açılışlarda yeniden derlenmeden kullanılıyor. JEP’e göre uygulama kodu değişikliği gerekmiyor, mevcut -XX:AOTCacheOutput / -XX:AOTCache akışı genişletiliyor. Kısıtlar arasında aynı CPU mimarisi ve özellik seti, tüm çalıştırmalarda aynı GC ve başlangıçta yalnızca AArch64 ile x64 desteği var.

JEP, iki çekirdekli bir Linux/x64 sistemde beş framework benchmark’ında yalnızca cache ile açılış süresinin yaklaşık %50⁠–⁠70, AOT kodla birlikte yaklaşık %65⁠–⁠80 kısaldığını bildiriyor.

Kaynaklar: OpenJDK · JDK 28 · JEP 544

BAĞLI ARAÇLAR · IAM

Bir otomobil üreticisinin admin aracında JavaScript’e gömülü OpenIDM parolası: plaka numarasıyla uzaktan komut zinciri

Assetnote kurucu ortağı Shubham Shah 7 Kasım’da, Sam Curry ile birlikte yürüttükleri ve adını vermedikleri bir otomobil üreticisinin bağlı araç altyapısındaki saldırı zincirini yayımladı. Zincir; internete açık bir iç admin aracı, JavaScript vendor paketine gömülü OpenIDM admin kimlik bilgileri, /static%2f..%2fopenidm/ biçiminde path traversal ile WAF atlatma, Resource Owner Password Credentials akışı üzerinden MFA atlatma ve ardından bir uygulama token’ı üretip uzaktan komut API’sini çağırmaktan oluşuyor.

Yazıya göre araştırmacılar Avustralya’da, yalnızca plaka numarasını bilerek üreticinin iki markasındaki herhangi bir araca kapı açma gibi komutlar gönderebiliyordu; çalışma ABD ve Kanada’yı da kapsıyor. Çalışma Temmuz 2026’da yapılmış. Yazıda etkilenen araç sayısı, ifşa takvimi ve üreticinin düzeltme durumu belirtilmiyor.

Kaynak: shubs.io

VİM

Vim 9.2.1308: /tmp’de önceden oluşturulan soket dizini, başka kullanıcının Vim’inde komut çalıştırmaya açıyor
